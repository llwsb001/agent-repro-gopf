# 性能测试

测试日期：2026-11-19（UTC），Zig 0.17.0，构建级别 **ReleaseFast**。

## 环境与命令

- 代理监听：`127.0.0.1:12482`（本轮按用户要求覆盖任务书的 12481）
- 后端：`127.0.0.1:18091`，现成 `bench/backend`
- 压测器：现成 `bench/load`
- 机器为共享环境，测试期间有其他 Agent 任务在运行，因此绝对值只作本轮草稿。

```bash
zig build -Doptimize=ReleaseFast
./zig-out/bin/gopf -listen 127.0.0.1:12482 settings.conf \
  >proxy-bench.log 2>&1

# 预热
load -addr 127.0.0.1:12482 -conns 50 -reqs 2000

# 正式测试，连续 3 次
load -addr 127.0.0.1:12482 -conns 100 -reqs 10000

# 大包
load -addr 127.0.0.1:12482 -path /big -conns 4 -reqs 100
```

## 小包结果

预热：

```text
reqs=2000 conns=50 elapsed=0.52s rps=3851 mean=12.84ms p50=11.67ms p99=51.66ms
```

三次正式测试：

| 轮次 | rps | mean | p50 | p99 |
|---|---:|---:|---:|---:|
| 1 | 4763 | 20.87 ms | 20.52 ms | 26.63 ms |
| 2 | 4414 | 22.52 ms | 22.39 ms | 27.41 ms |
| 3 | 4410 | 22.53 ms | 22.53 ms | 26.58 ms |
| **中位数** | **4414** | **22.52 ms** | **22.39 ms** | **26.63 ms** |

## 大包结果

`/big` 每次返回 1 MiB，`-conns 4 -reqs 100`：

```text
reqs=100 conns=4 elapsed=0.17s rps=580 mean=6.85ms p50=6.63ms p99=11.18ms
```

按工具给出的 580 req/s 和每次 1 MiB 计算，代理大包吞吐约为 **580 MiB/s**
（约 608 MB/s）。

## 与基线对照

任务书给的 Go 原版基线是 **15.7k rps，p50 6.0 ms，p99 13 ms**；直连后端
**30.9k rps**。本轮 Zig 中位数是 **4.4k rps，p50 22.39 ms，p99 26.63 ms**，
约为 Go 原版 rps 的 28%，p50 约为其 3.7 倍。

为区分“实现差距”和“当前共享机器负载”，本轮还用同一个压测器直连了后端一次：

```text
reqs=10000 conns=100 elapsed=0.39s rps=25387 mean=3.87ms p50=3.42ms p99=10.96ms
```

当前直连只有任务书基线的约 82%，说明机器本身已有争用；但 Zig 代理相对当前直连
仍只有约 17% 的请求吞吐，主要差距来自线程模型：

1. `bench/load` 每个请求新建一条 TCP 连接。Go 版每条连接用两个 goroutine，创建
   和切换在用户态完成，网络阻塞由 netpoller 接管。
2. 本实现每条连接创建一个工作线程，再创建一个反向拷贝线程；即约 2 次
   `clone`/调度实体创建、2 份内核栈映射。线程创建和回收成本直接落在每次请求上。
3. 每个连接还要执行 accept、5 秒超时所需的非阻塞拨号配置、6 次左右 keepalive
   `setsockopt` 和逐连接 accept 日志。日志已重定向到文件，但格式化/write 仍在
   热路径。
4. 数据拷贝使用两个 16 KiB 栈缓冲区，没有每连接堆分配；这部分不是主要瓶颈，
   当前瓶颈是每请求的线程生命周期和系统调用次数。

大包场景受线程创建影响较小，主要受拷贝和 syscall 吞吐影响，因此仍达到约
580 MiB/s。若要进一步提升小包 rps，优先方案是固定 worker pool 加事件循环：
每个 worker 用 `poll` 同时驱动多个连接的两个方向，避免每请求创建线程；其次可把
accept 日志改为异步批量输出。
