# 性能测试

## 环境与编译级别

- 机器：Linux x86_64，4 vCPU（共享测试机，测试时机器上还有其他 Agent 的压测/编译任务）。
- Zig：0.17.0，编译级别 **ReleaseFast**：
  ```bash
  zig build -Doptimize=ReleaseFast
  ```
- 后端：任务书提供的现成 `bench/backend`，监听 `127.0.0.1:18091`，`/` 返回 396 字节，`/big` 返回 1 MiB。
- 代理：`./zig-out/bin/gopf -listen 127.0.0.1:12483 settings.conf`，配置指向 `127.0.0.1:18091`。
- 压测器：任务书提供的现成 `bench/load`，没有另写压测器。

说明：本轮调度要求代理监听 12483（12481 被其他实例占用）；配置仍指向 18091 后端。测试机有并发负载，下列数字是可复现流程下的一次完整记录，绝对值会随机器负载波动。

## 小包（默认 `/`，396 字节响应）

先预热，再连跑 3 次取中位数：

```bash
bench/load -addr 127.0.0.1:12483 -conns 50  -reqs 2000    # 预热
bench/load -addr 127.0.0.1:12483 -conns 100 -reqs 10000   # 正式，跑 3 次
```

| 轮次 | rps | p50 (ms) | p99 (ms) | mean (ms) |
|---|---:|---:|---:|---:|
| 预热 50/2000 | 11711 | 3.45 | 16.18 | 4.17 |
| 正式 1 | 16658 | 5.67 | 12.58 | 5.96 |
| 正式 2 | 15870 | 5.97 | 11.55 | 6.21 |
| 正式 3 | 16269 | 5.92 | 12.28 | 6.08 |
| **中位数** | **16269** | **5.92** | **12.28** | **6.08** |

## 大包（`/big`，1 MiB 响应）

```bash
bench/load -addr 127.0.0.1:12483 -path /big -conns 4 -reqs 100   # 跑 3 次
```

| 轮次 | rps | p50 (ms) | p99 (ms) | mean (ms) |
|---|---:|---:|---:|---:|
| 大包 1 | 478 | 7.57 | 24.30 | 8.28 |
| 大包 2 | 502 | 7.00 | 15.23 | 7.83 |
| 大包 3 | 537 | 6.73 | 13.98 | 7.32 |
| **中位数** | **502** | **7.00** | **15.23** | **7.83** |

每请求有效载荷 1 MiB：

- 吞吐 ≈ 502 × 1 MiB/s = **502 MiB/s ≈ 526 MB/s**（按 1 MiB = 1.048576 MB）。
- 按中位请求耗时 0.199 s / 100 个请求算：100 MiB / 0.199 s ≈ 502 MiB/s，与上面一致。
- 大包 p99 的波动主要来自 1 MiB 数据要经过两次用户态 32 KiB 缓冲拷贝，以及共享机器上其他任务的干扰。

## 与 Go 原版基线对照

任务书给出的同机 Go 基线：

| 指标 | Go 原版 gopf | 本 Zig 版（3 次中位） |
|---|---:|---:|
| 小包 rps | 15.7k | **16.27k** |
| p50 | 6.0 ms | **5.92 ms** |
| p99 | 13 ms | **12.28 ms** |
| 直连后端 rps | 30.9k | 同轮实测 27.1k |
| 大包吞吐 | 未给 | **502 MiB/s ≈ 526 MB/s** |

同轮直连后端实测为 27.1k rps（p50 3.20 ms、p99 12.10 ms），比任务书基线 30.9k 低约 12%，说明测试时机器本身有额外负载；因此 16.27k 对比 15.7k 应理解为“同一量级、略高”，不要过度解读小数差异。

差距/表现来源：

1. **线程模型**：Go 原版每连接至少一个 goroutine，双向 `io.Copy` 再各一个 goroutine，由 Go runtime 的 netpoller 在多核间调度；Zig 版是单线程 epoll 事件循环，线程数恒定。短连接小包场景中，省去的线程创建、调度器唤醒和每连接 `poll` 开销抵消了单核限制，因此 rps 略高。若并发继续增大或需要吃满多核，应改为 `SO_REUSEPORT` 多事件循环/多 reactor。
2. **系统调用路径**：Zig 版把就绪事件批量取出，一个连接在一次事件循环里完成读→写；Go 版依赖 runtime netpoller + 阻塞式 Read/Write 的 goroutine 唤醒。两条路径各有开销，本机短连接下 Zig 的事件循环略占优。
3. **内存与分配**：Zig 版启动时一次性分配 1024 个连接槽（每槽两个 32 KiB 缓冲），数据面热路径不做堆分配；Go 版 `io.Copy` 每方向会分配 32 KiB 缓冲并依赖 GC。Zig 版少了一次次分配/回收，但固定槽位也意味着超过 1024 并发连接会被拒绝。
4. **单核上限与拷贝**：Zig 版所有连接共享一个事件循环核，且用户态缓冲区需要两次拷贝（socket→buf→socket）；Go 版可多核并行，但同样有用户态拷贝。因此大包吞吐受单核内存带宽和拷贝次数限制，约 500 MiB/s。
5. **共享机器**：压测时其他 Agent 仍在跑负载，rps/p99 有明显轮间波动；表中保留了三轮原始值和明确的中位数口径。

## 复现命令汇总

```bash
zig build -Doptimize=ReleaseFast
./zig-out/bin/gopf -listen 127.0.0.1:12483 settings.conf >/tmp/gopf-proxy.log 2>&1 &

BENCH=/home/user/Doubao/chats/38453552245765378/zig-gopf/bench
$BENCH/load -addr 127.0.0.1:12483 -conns 50  -reqs 2000
$BENCH/load -addr 127.0.0.1:12483 -conns 100 -reqs 10000   # ×3，取中位
$BENCH/load -addr 127.0.0.1:12483 -path /big -conns 4 -reqs 100   # ×3
$BENCH/load -addr 127.0.0.1:18091 -conns 100 -reqs 10000  # 同轮直连对照
```
